# Architecture

Panelavo is a single Next.js App Router application deployed as a CloudPanel Node.js site. Nginx/CloudPanel terminates public TLS and proxies the panel domain to the single PM2-managed Next.js process bound only to `127.0.0.1:10443`. The installer gives the public proxy a 1,900-second read/send timeout so synchronous Operations and Backups requests can complete within the application's roughly 30-minute bound. Port 10443 is not a public authentication surface; emergency direct access uses an SSH tunnel.

Browser requests enter pages and route handlers in `src/app`. Shared validation lives in `src/schemas`; UI components live in `src/components`. Protected server routes obtain opaque application sessions from `src/server/auth`, revalidate current CloudPanel identity and roles, and call the live adapter in `src/server/cloudpanel`. Versioned automation routes authenticate scoped HMAC-digested bearer tokens, while the remote MCP route accepts user-created bearer tokens or same-origin OAuth and dynamically exposes role-appropriate website tools; both perform the same current-user revalidation and shared actor-aware service calls. The adapter sends bounded JSON over stdin to `/usr/local/libexec/panelavo/panelavo-broker`, the only Panelavo-owned sudo command. `setup.sh` installs that broker and its PHP bridge root-owned outside the mutable application tree. The broker validates its protocol and allow-listed operations before using CloudPanel's CLI or Symfony/Doctrine internals. CloudPanel remains authoritative for users, roles, MFA, sites, assignments, site types, runtimes, the NGINX serving/document root, and upstream settings. Panelavo's `.data/site-roots.json` overlay stores an optional application root for repository and command-oriented features; without an override it falls back to CloudPanel's serving root.

Cloudflare-backed domain pointing uses one server-side `pointDns` policy for site creation, SSL preparation, and the explicit DNS route. It ensures the primary A record plus the applicable `www` companion and returns structured per-name outcomes; each caller decides whether a failure is fatal, logged, or an acceptable companion warning.

The bridge validates both roots beneath `/home/<site-user>/htdocs`. The application root is the workspace used by Git, File Manager, Terminal defaults, Environment, Operations, cron working-directory guidance, and backups; the serving directory is passed to CloudPanel and NGINX, so a PHP/static site can serve `<root>/public` while Panelavo continues to manage the repository root. Existing sites retain prior behavior until an application-root override is saved. The bridge executes allow-listed Git operations as each site's Unix user. Git is non-interactive, uses that user's home and deployment key, records new SSH host keys with OpenSSH's `accept-new` policy, and is bounded by a five-minute timeout. Clones are restricted to empty configured application roots so existing application files cannot be overwritten. The one safe scaffold exception records a root-owned creation-time filename/size/SHA-256 manifest for small regular top-level files on new PHP sites. Clone revalidates that exact manifest after fetching into a temporary child, preserves `.well-known`, stages the unchanged scaffold, promotes the complete repository, restores the original files if promotion fails, and consumes the manifest only after success. Edited content, extra entries, links, and directories remain blocked. Working-tree paths come from NUL-delimited Git status output and are revalidated against live status before per-file diff or discard operations. Diff content is loaded only when a file is selected. Pulls preserve dirty tracked and untracked work through an automatic stash/restore cycle; a conflicted restore leaves both conflict markers and the safety stash for recovery. Per-site after-pull plans persist up to ten narrow Operations in `.data/deploy-hooks.json`; the broker re-resolves them from current preflight state and holds the normal site lock across both the pull and ordered execution.

File-manager uploads use base64 JSON and are limited to 64 MiB decoded at both browser and bridge boundaries. MCP has a separate binary artifact channel under `/api/mcp/artifacts/<id>`: metadata in `.data/mcp-artifacts.json` binds each 24-hour upload to one stable actor, MCP credential, and website; private partial bytes live under `.data/mcp-artifacts`; sequential raw chunks are limited to 32 MiB and must match `Content-Range`, the declared total (up to 2 GiB), and the final SHA-256. Per-actor count and byte quotas bound storage. The panel Nginx vhost accepts request bodies up to 96 MiB and disables proxy request buffering so chunks stream without an extra proxy-temporary copy; `setup.sh` owns those directives and applies them with validation and rollback. Archive extraction may target a folder that does not exist yet: the bridge validates each path segment, rejects traversal and symlinked levels, creates the missing directories owned by the site user, and re-verifies containment before extracting. tar.gz/tgz extraction additionally preflights every member name and type, rejecting absolute/parent paths, links, and special entries before running tar as the site user.

Per-site environment management treats the application root's `.env` (plus `.env.local` and `.env.production`) and the site user's login environment as one synchronized surface. The bridge parses and rewrites dotenv files while preserving comments and unknown lines, and mirrors the primary `.env` into a marker-tagged `export` block in `~/.profile` — everything outside the markers is preserved. PM2 launches additionally inject the site's `.env` (filtered to safe key shapes and sizes; reserved variables and `LD_*` are skipped, and CloudPanel's expected `PORT` wins), so a process's live environment matches the configured one without the application parsing `.env`. Environment reads return secret values, so the panel loads them only for users with site-write access; the Operations runtime payload carries key names and sync verdicts only. When Compose reports missing variables, Operations may submit values only for those detected keys through a bounded upsert; the bridge merges them into `.env` without returning or replacing unrelated secrets.

Per-site backups are on-server snapshots the bridge builds under `/home/<site-user>/backups/<id>/`: a gzip tar of the application root archived as the site user, plus a `clpctl db:export` gzip of each selected database (run as root, then chowned to the site user), described by a `manifest.json`. Creation is atomic — any failed step deletes the partial snapshot directory, so a listed backup is always complete — and a configurable retention pass keeps the newest 1–100 snapshots by timestamp id. Daily or weekly UTC schedules live in `.data/backup-schedules.json`; a single in-process minute timer claims each due slot durably before invoking the protocol-versioned broker action. Backup jobs take the same non-blocking per-site operations lock as deployments, so a busy scheduled run is skipped and its outcome is recorded rather than queued twice. Restore extracts the archive over the live tree (an overlay, not a clean-room replacement) and imports databases only into databases that still belong to the site; a database removed since the backup is skipped because the bridge cannot recreate it without credentials. Snapshots live inside the site home so they are reachable through the File Manager and SFTP without a bespoke large-file download path, and the section is loaded only for users with site-write access.

Off-site destinations are per-site S3-compatible configurations encrypted with AES-256-GCM under `.data`. The Node server uses the AWS S3 client, but it never receives general read access to a site's home. Protocol 7 lets the root-owned broker package one validated snapshot into a caller-owned mode-0600 file under `/run/user/<panel-uid>/panelavo-backup-staging`; Node streams that file to the configured bucket and removes it. Downloads reverse the flow: Node streams the object into that private staging directory, and the bridge rejects traversal, links, unexpected archive members, or a mismatched manifest before atomically importing the site-user-owned local snapshot. The existing local restore implementation remains the only path that mutates live site files and databases.

The per-site Terminal executes one browser-submitted command line as the site's Unix user — deliberately a user-supplied command, unlike Operations' fixed argument arrays, because the boundary is the same unprivileged Unix account the user could reach over SSH. The bridge runs it through `sudo -u <site-user>` in an emptied environment via a non-interactive `bash -l -c` login shell (so the managed profile block applies), with a validated working directory contained in the site home, a three-minute kill timeout, bounded output, and a random per-invocation marker that captures the final working directory so `cd` persists between commands. It never runs as root and grants nothing the site user's SSH session would not.

Project access is a broker-enforced invariant. When an authorized workspace or section is opened, and again before a section mutation, the root-owned bridge verifies that the configured application root has a named POSIX ACL granting its CloudPanel site user `rwX` access and an inheritable default ACL. A missing invariant triggers one physical, non-symlink-following traversal contained under `/home/<site-user>/htdocs`: existing paths receive `rwX` and every directory receives the default entry so files subsequently created by containers or other runtime UIDs remain manageable by Git, backups, the File Manager, Environment manager, and Terminal. Ownership is preserved, execute permission is added only to directories or already-executable files, and no access is granted to other users. `setup.sh` installs the required `acl` package; a missing tool blocks with trusted-installer guidance.

The Super Admin update API reads a configurable public HTTPS Git repository from the panel settings store. Checks use `git ls-remote`; installs launch the non-root `scripts/self-update.sh` worker. The worker holds a `.data` lock, shallow-clones `main`, verifies the Panelavo package contract and declared broker protocol, and refuses the release before build or deployment unless the installed root broker passes its health handshake. It then installs from the frozen pnpm lockfile and completes a production build in staging before synchronizing the live tree. While the persisted state is queued, updating, or reloading, the shared panel layout blocks interaction and authenticated APIs reject normal operations, while server-rendered panel pages remain available behind the overlay. It excludes `.data` and `.env.local`, records durable status and logs, then cleans staging and records the old process PID before asking PM2 to reload. Because PM2 kills the worker with the old process tree, the replacement Panelavo process owns completion of this PID-bound handoff. Legacy states whose installed and remote commits already match are recovered automatically, including removal of their stale update lock. The repository is a trusted application-code source but receives no root execution path; broker upgrades require a separately trusted root `setup.sh` run.

Application-owned metadata, persistent request-throttling counters, and encrypted credentials live under `.data` in the deployed site. Plain JSON overlays use the shared `src/server/storage/json-store.ts` fallback and serialized atomic-write policy while remaining separate compatibility files. Pending MFA enrollment secrets use the encrypted store, expire after ten minutes, and reach CloudPanel only through the allow-listed broker action after CloudPanel's verifier accepts a TOTP code. The address mode, base domain, and public update repository come from explicit `.data/panel-settings.json` values or `.env.local` seeds. Address-mode migration is inferred safely: `sslip.io` means sslip mode and every other existing base domain means custom mode. Host configuration comes from `.env.local`; secrets must not reach client components except the one-time MFA provisioning payload intentionally shown to its authenticated owner. A single process is required by the current session and mutation-serialization design.

`src/server/auth/site-access.ts` is the shared site authorization boundary. It resolves the authenticated actor's current upstream site collection before any site-scoped local overlay is read or mutated, deliberately returning the same 404 for missing and unassigned domains. Domain and alias authorization derives ownership only from metadata attached to that live visible collection, so deleted-and-recreated domains cannot inherit stale caller access.

`src/server/sites/site-service.ts`, `site-section-service.ts`, `site-domain-service.ts`, `linked-service-service.ts`, and `site-automation-service.ts` are actor-aware orchestration boundaries shared by browser sessions and the applicable automation surfaces. They accept an actor containing the live decorated CloudPanel user and a CloudPanel session, then apply the same create/update/delete sequence, site-section allowlist, high-level domain/DNS/SSL and linked-service workflows, typed schemas, write checks, deployment hooks, monitoring and backup automation policy, and long-running-operation collision guard before reaching the decorated CloudPanel client. Local metadata is never consulted for a target until its live site visibility has been established.

`src/server/mcp` owns the public MCP surface. `public-url.ts` derives one canonical HTTPS issuer and resource from the configured panel self-domain. The AI access page can issue named personal MCP tokens with fixed 30-, 90-, or 365-day expiry; each secret is revealed once, bound to that resource and the stable CloudPanel subject, and retained only as an HMAC digest. OAuth discovery is available at the authorization-server and both protected-resource well-known paths. `/oauth/register` accepts bounded public dynamic clients with exact HTTPS or loopback redirects. `/oauth/authorize` uses the ordinary revalidated Panelavo browser session and explicit consent. S256 PKCE binds the one-use five-minute code to client, redirect, and resource. `.data/mcp-oauth.json` contains only HMAC digests of personal tokens, codes, and OAuth access/refresh tokens plus stable CloudPanel subject ids, client metadata, and grant lifecycle state. Fifteen-minute OAuth access tokens and rotating refresh tokens are bound to `https://<panel-domain>/mcp`; replay revokes their family. All store mutations are serialized across load-modify-save so issuance, one-use operations, usage timestamps, revocation, artifact offsets, artifact finalization, and background-job transitions remain atomic in the required single process.

`.data/mcp-jobs.json` is the bounded durable journal for MCP deployments, backups, and allow-listed Operations. Each record is bound to the stable actor, originating MCP credential, and system domain; status and cancellation also recheck current writable-site access. One actor cannot overlap jobs on one website. Job output is limited to server-owned lifecycle messages, 100 short log entries, and a 64 KiB result summary; history is limited to 100 jobs per actor and seven days. Resolved broker results are classified as failed when their aggregate run or any reported step times out or returns a nonzero exit code, and the bounded result remains attached for diagnosis. A process restart marks orphaned active records interrupted rather than implying success. Runtime `AbortController` instances are intentionally in-memory and are threaded through the actor-aware site service to the privileged broker invocation. On cancellation or timeout, Panelavo kills the detached broker process group, including its allow-listed site-user descendants. The existing per-site Operations lock remains the second concurrency boundary.

Managed artifact releases use `/home/<site-user>/htdocs/.panelavo-releases/<application-root-hash>/releases/` for versioned site-user-owned trees. The configured application root must be a non-mounted directory below `htdocs`; first activation moves it into the release set and replaces it with an atomic symlink pointer, while later activation renames a prepared temporary pointer over that symlink. The root broker accepts only a completed MCP tar.gz path owned by its exact unprivileged caller under that caller's `.data/mcp-artifacts`, re-hashes it, rejects traversal, links, special entries, excessive entry count, and unpacked size above the lesser of 10 GiB or 70% of current free space, then validates required paths. Existing `.env`, `.env.local`, and `.env.production` files are copied into the staged tree without exposing their values. Operations preflight is resolved against the staged release before activation. The selected server-owned non-Compose plan and a local-Nginx HTTPS health path gate success; failure atomically restores and redeploys the previous pointer. Rollback uses the same gate, and successful operations retain at most ten releases. Compose is excluded until bind-mount and datastore inventory can be verified as part of activation.

Selective LanceDB handling is a separate MCP-only workflow for safe rootless Compose sites. The broker inventories only physical `<table>.lance` directories under a validated application-root-relative datastore path and requires the Lance `_transactions`, `_versions`, and `data` subtrees without symlinks. Include/exclude globs select whole tables. Snapshot creation stops the exact rootless Compose project, writes a checksum-bound tar and manifest under `/home/<site-user>/backups/datastores/<id>/`, then restarts and probes the caller-selected readiness path. Restore verifies that manifest and SHA-256, stages and structurally validates the chosen tables, stops Compose, atomically renames whole table directories, then restarts. Same-site readiness plus up to ten numeric JSON field assertions gate success; failure stops the project again, restores the prior table directories, and attempts the same restart/readiness gate. These snapshots do not replace whole-site backups and do not yet make Compose artifact activation data-aware.

Controlled recovery does not expose a root command surface. The MCP proxy diagnostic maps only to the existing bounded `upstream-check` against CloudPanel's stored URL. Mutating recovery accepts exactly `repair-site-acl`, `restart-rootless-runtime`, or `recover-rootless-migration`, takes the existing per-site broker lock, and runs as a cancellable background job. ACL repair reapplies only the named/default site-user ACL invariant below the configured root. Runtime restart targets only that Unix user's private rootless daemon and refuses an unprovisioned host. Journal recovery remains CloudPanel Super Admin-only and uses the existing retained ownership journal, legacy rootful restart, and endpoint verification sequence. No operation accepts a path, unit, socket, service name, or shell command from MCP.

Bearer verification re-fetches the current decorated CloudPanel user on every MCP HTTP request and rejects a disabled, deleted, or same-name/recreated account by comparing the stable CloudPanel id. Personal tokens and OAuth grants therefore share the same live authorization boundary. The MCP server is built per request from that live actor, so role-inaccessible tools are absent from `tools/list`; tool handlers still recheck the current visible site collection and broker authorization at execution. Sensitive tools use MCP elicitation for a separate signed-in-user approval. `.data/mcp-confirmations.json` holds only expiring pending nonces; HMAC-authenticated request state binds each one-use approval to the MCP method, stable actor, MCP client, credential, exact tool, and canonical argument digest. Deletion additionally requires the exact domain. Tool handlers never call Panelavo over HTTP: they pass bounded typed input into the shared actor services and allow-listed bridge. The single capability label, `panelavo:access`, does not encode or cache roles or assignments. Account credentials, MFA, sessions, Panelavo account administration, panel settings, and the browser-only one-time phpMyAdmin sign-in are intentionally not MCP tools.

Optional site labels live in `.data/site-labels.json`. Site creation receives the authoritative new record from the root bridge before persisting its label. Each label record is keyed by normalized system domain and contains that upstream site-record ID; reads ignore records whose ID no longer matches. Category presentation is derived from `site-meta.json` and the canonical `SITE_CATEGORIES` order, while upstream-only sites are presented as Uncategorized.

Panel-wide notification channels live in the AES-256-GCM encrypted `.data/notification-settings.enc` store. `src/server/notifications` sends bounded SMTP email through Nodemailer and generic HTTPS webhook JSON with channel-specific compatibility fields. Only Super Admins can read the redacted configuration, save it, or trigger a delivery test; stored SMTP passwords are never returned to client code.

Monitoring reuses the single-process runtime. The existing one-minute resource sampler feeds a persisted threshold state machine that requires N consecutive breach samples before alerting and N healthy samples before recovery. A companion minute timer claims due per-site HTTPS checks from `.data/monitoring.json`; each primary domain has its own 1–60 minute interval and persisted up/down/failure state. Checks do not follow redirects, consider HTTP 2xx/3xx healthy, and use bounded timeouts. Enabled sites receive a direct TLS expiry check at most every six hours. The same timer checks the configured update repository every six hours, while scheduled-backup failures publish directly. Notification delivery failures never take down sampling or hosted websites.

The `/resources` route does not synchronously collect privileged metrics. It renders with persisted history, then the client requests a twenty-five-second, in-flight-deduplicated server snapshot and polls every thirty seconds only while visible. The bridge samples machine and per-PID CPU in one bounded window, uses `/proc/<pid>/smaps_rollup` PSS for proportional shared-memory accounting with RSS as an explicit fallback, and resolves each process through application-root evidence, unique site-user ownership, rootless cgroup ownership, or uniquely matched root-Docker Compose/path/port metadata. A process that maps to multiple websites stays in the Shared bucket; a host process with no website evidence stays in System. Root-owned PHP/application processes can therefore be attributed by a contained working directory or command path, while shared Nginx/database masters are not falsely split. Per-application-root disk totals are cached for ten minutes, refreshed by one three-second-bounded `du` pass, and marked shared when multiple website records use the same root. Disk-detail analysis is a separate authenticated request so it never delays the live polling contract. A root-owned lock serializes scans, which run at low CPU and idle-I/O priority over at most 32 validated root-filesystem paths under a five-minute broker bound; complete results are cached for thirty minutes (incomplete bounded results for one minute). Groups use disjoint allocated-block totals for site-user homes, other `/home` data, operating-system files, `/var` service data, administrator data, temporary data, and a residual filesystem-overhead/unclassified bucket; a device check excludes separate mounts. `df` supplies allocated, available, and filesystem-reserved capacity. Per-site-user Docker summaries are drill-down metadata, not additive group totals, because Docker image and BuildKit figures can share layers. A separate Super Admin-only, explicitly confirmed host action serializes across cleanups and invokes only bounded `docker builder prune --all --max-used-space 5000000000` commands against each exact site-user socket; daemons without the bounded flag are skipped, and containers, images, volumes, databases, backups, and application roots remain outside its deletion scope. The legacy per-user array remains in the API for compatibility, but the UI, filtering, sorting, and pagination use the website attribution model.

Audit events are redacted before they are serialized into the bounded, rotated, hash-chained `.data/audit` ledger. The Super Admin-only `/audit` page and `GET /api/audit` call the same pagination/filter path, which verifies retained event hashes, inter-event links, and the persisted head before returning results; reads never bypass the ledger lock.

## Managed website Operations

The CloudPanel site type, including Panelavo's Docker overlay for CloudPanel reverse-proxy records, is authoritative. `scripts/cloudpanel-bridge.php` inspects only the configured application root and returns structured architecture evidence, manifests, declared scripts, installed tool versions, permissions, PM2 state, Compose capabilities, and validation results. The same report carries a runtime snapshot — PM2 process details, the Compose project's container states/health/published ports, site-owned listening sockets, and a values-free `.env` drift verdict per key — sampled synchronously per request; there is no background polling or streaming. `src/server/sites/site-operations.ts` converts that report into a primary architecture, alternatives, explicit preflight checks, action groups, and a recommended server-owned plan. A manifest can be detected while every related action remains blocked because its runtime, configuration, permission, or safety check failed.

The adapters cover npm, pnpm, Yarn, and Bun lockfile selection; Composer with Laravel and WordPress actions; Python through uv, Poetry, Pipenv, or pip plus Django actions; direct static sites; reverse-proxy checks; PM2 process management; and Docker Compose. The configured root is not searched recursively. A JavaScript workspace therefore needs usable root scripts or explicit root-level configuration, and Panelavo does not guess a generated static output directory or change the CloudPanel document root automatically.

The browser submits only a validated action identifier plus a narrowly validated script or process name when required, or a known deployment-plan identifier. The server expands these into fixed executable argument arrays, a fixed working directory, bounded time and output, and no shell, re-verifying every preflight precondition at execution time. Commands run in an emptied environment (no panel or CloudPanel secrets) whose PATH covers the site user's Node.js, Bun, Composer, and Python tool directories, with Poetry, Pipenv, and pip pinned to project-local virtual environments. A per-site operation lock rejects overlapping runs, plans stop after the first failed step, and the UI keeps missing tools and other blockers visible instead of attempting fallback installation.

Each Docker site has an independent rootless daemon, socket, object namespace, and data store owned by its CloudPanel site user. The bridge injects `HOME`, `USER`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`, and the exact `unix:///run/user/<uid>/docker.sock` only into Docker/user-systemd helpers; the ordinary empty-environment runner is unchanged and there is no root-socket fallback. Resolved runtime files are site-owned mode 0600 inside a validated mode-0700 directory under that runtime directory and are deleted after use. Ordinary Compose lifecycle actions use the same site-user/SSH boundary as Terminal and therefore require site-write access, not Super Admin approval. Safety still blocks privileged mode, capabilities, devices, host/shared namespaces, unsafe security options, and out-of-root mounts/build contexts.

Rootless initialization is an allow-listed Super Admin host action. It verifies Docker Engine/CLI, Compose v2, Buildx, rootless extras, functional uidmap helpers, D-Bus, slirp4netns, non-overlapping subordinate ranges, cgroup v2/systemd, storage, linger, user-manager ownership, bus, and socket. It starts the user's systemd manager before running the setup tool and enables the user Docker service. The setup-created rootless context supports interactive SSH without a profile `DOCKER_HOST` override. Per-site stores under `~/.local/share/docker` duplicate shared image layers and are intentionally outside application-root backups; readiness reports their disk/reclaimable use and free space. Userspace port forwarding may change the immediate peer address observed inside containers, so application authorization must use CloudPanel's trusted forwarding configuration.

Migration from legacy rootful Compose is two-phase and Super Admin-only. Preparation performs one cold pull/build per bounded request without creating containers or interrupting traffic, rejects named/external volumes and unsafe or conflicting bind ownership, then stores an expiring root-owned manifest of configuration/image/container identities, subordinate ranges, ports, bind sources, and ownership inventory. Runtime identity resolution uses the running PID directly when it is non-root; for a root init wrapper or privilege-dropping entrypoint, one unique non-root application identity is accepted, while multiple non-root identities remain ambiguous and block migration. Cutover revalidates every input, retains stopped rootful containers, writes a path-safe ownership journal, translates root to the site UID/GID and container id `n >= 1` to `subordinateStart + n - 1`, and reapplies recursive named/default site-user ACLs. A mapped non-root runtime UID receives traverse-only ACLs on the contained path ancestors and inherited `rwX` access inside its writable bind; pre-existing mapped-UID entries block preparation so these additions can be removed deterministically on rollback. It starts the prepared rootless configuration with `--no-build` and verifies state, health, ports, bind access, and HTTP. Failure removes the partial rootless project, restores journaled ownership including newly created mapped files, removes migration-added runtime ACLs, reapplies the site-user ACL invariant, and restarts/verifies rootful service. A stale journal blocks new migration until explicit recovery succeeds.

The configured CloudPanel upstream/app port is the runtime contract for every port-based site. The bridge compares that expected port with site-owned listening sockets. Node and Python PM2 starts receive `PORT`, `HOST`, and `HOSTNAME` values for the expected loopback endpoint; reverse-proxy sites verify their configured upstream. Recommended plans finish with a bounded HTTP probe and fail instead of claiming success while Nginx would return 502. A site-scoped port repair is exposed only when the bridge independently identifies one unique `.env` numeric `PORT` without another easy override, or one unique literal Compose entry mapping. Execution re-resolves the plan under the per-site lock, stages the edit beside the source, validates dotenv or resolved Compose routing plus host safety, retains a verified 0600 root-owned backup under `/var/lib/panelavo/port-source-backups`, and atomically replaces the source without restarting services. Ambiguity produces file-specific instructions rather than a mutation.

Site creation derives an omitted reverse-proxy upstream from the allocated site id as `http://127.0.0.1:<site-id>`. This keeps the CloudPanel vhost and the reserved application port aligned by default while preserving explicit custom upstreams. After aliases and DNS preparation, creation awaits its initial Let's Encrypt issuance attempt; ACME failure does not roll back the already-created website, but it returns an explicit Security-tab retry warning instead of detaching the work.

Project endpoints close the loop on reported additional ports. The bridge inventories only high loopback listeners proven to belong to the parent site's Unix UID or contained application tree, and rejects wildcard/public listeners, foreign processes, and ports reserved by another CloudPanel site. The actor-aware endpoint service rechecks live parent write access and records `parent`, `serviceName`, `targetPort`, and pending state in `.data/site-meta.json`. A stopped port stays a non-public reservation with no CloudPanel child; successful ownership and HTTP verification activates a normal reverse-proxy site at `http://127.0.0.1:<port>`, with a panel-derived id, system domain, aliases, and SSL. Active port changes are probed before and after the NGINX update and restore the previous upstream on failure; generic child-site updates cannot set the proxy URL, and endpoint children cannot access the raw vhost editor. Endpoint sites expose only settings, domains, certificates, security, and users. Parent deletion returns 409 while endpoints exist, and endpoint deletion removes only its reservation or child proxy.

For Compose, Panelavo resolves the configuration to JSON and selects one public entry service using, in order, an existing exact mapping, an explicit `io.panelavo.entrypoint=true` label, a unique port candidate, the dependency graph, or an unambiguous conventional gateway name. The container port comes from `io.panelavo.container-port`, an exact publication, or consistent port/environment/health-check evidence. An unambiguous mismatch is mapped at execution time to `127.0.0.1:<expected-port>` in the private ephemeral configuration; Compose-generated null or empty network IPAM placeholders are removed while real IPAM mappings are preserved and all other published ports are also restricted to loopback. The optional port repair may persist that same policy only when one literal short entry mapping can be rewritten and the full staged source still resolves safely; Dockerfile EXPOSE and container environment ports remain internal and unchanged. Ambiguity blocks deployment and reports the exact label or mapping needed. Additional service ports remain private and are reported so the operator can expose each one through a connected CloudPanel reverse-proxy site belonging to the same application.

Site deletion treats the Unix-account lifetime as load-bearing: the bridge first removes that site's rootless containers, images, volumes, and migration state, stops/disables its user Docker service, removes the private Docker data after explicit destructive confirmation, disables linger, and verifies the manager/socket are gone. Only then may CloudPanel delete the site and Unix user. Other users' rootless daemons and unrelated rootful workloads are outside this cleanup scope.

Blocked host-software checks carry explicit one-click fixes when Panelavo can safely resolve them. Docker/Compose host installation (including the shared rootless packages and subordinate ID ranges, which `setup.sh` also provisions) and Composer installation remain Super Admin-only, individually confirmed, and host-wide serialized. Once the host is provisioned, starting a site user's own rootless runtime is a site-write self-service fix — authorized like any site operation and serialized per site. The port-source repair uses that same site-write/per-site boundary and never restarts a process. Neither site-scoped fix installs packages or allocates subordinate ranges. Violations that require operator judgement — privileged mode, host namespaces, out-of-root mounts, or ambiguous port authorities — are never rewritten automatically and retain instructional remediation.

Operations currently run synchronously within one bounded HTTP request and mutate the configured live application root. They do not create release directories, atomically switch releases, or provide automatic code or database rollback. Laravel and Django migrations remain separate destructive actions rather than automatic plan steps; an operator must arrange a database backup and recovery procedure before running them.

Installation offers exactly two address modes: sslip.io is recommended and selected by default, while custom mode requires one wildcard A record and waits for it to resolve. Existing base domains are inferred as sslip only when equal to `sslip.io`; all others remain custom. Explicit `PANEL_DOMAIN` overrides are preserved, generated hostnames are verified directly, and the installer issues individual HTTP-01 certificates because sslip.io does not provide wildcard certificates.

`setup.sh` detects supported Debian/Ubuntu versions, installs prerequisites and CloudPanel when absent, publishes a complete non-root-readable Node.js distribution in `/usr/local/lib/panelavo-node`, and uses `npx` with the pinned pnpm version so Corepack is optional. It creates the panel site/user, deploys and builds the repository, configures narrow sudo access, starts PM2, and configures firewall rules and SSL. Generated account credentials are written to a root-only pending handoff before account creation, reused after an interrupted setup, and deleted only after successful completion; an explicit Admin password can reset the matching account during recovery. It also provisions a standalone phpMyAdmin database manager as an ordinary CloudPanel PHP site on `database.<ip>.<base-domain>` with its own Let's Encrypt certificate and records the address in `DATABASE_MANAGER_URL`; the panel's database links target that host (no root logins, local MySQL only) instead of CloudPanel's self-signed, firewalled port-8443 portal, and the manager's site — like the panel's own — is hidden from listings and protected from per-site operations. "Manage" performs a one-time sign-on: the root broker verifies site-write access and database ownership, reads the database user's password from CloudPanel's encrypted store, and writes it into an expiring 0600 token file in the manager site user's private `~/.pma-signon` directory; the browser carries only the random token to `signon.php`, which consumes it once and hands phpMyAdmin a signon session. "Open phpMyAdmin" keeps plain cookie login with the database user's own credentials. Provisioning leaves fail2ban's `sshd` jail active; an optional detected-client exemption is temporary and removed on exit. It recovers SSH connection metadata through process ancestry and preserves the live SSH port in UFW. Existing active UFW installations are updated; inactive UFW installations receive prepared rules but are activated only through the explicit `ENABLE_UFW=true` opt-in.
